🏗️ Omnigent 多角色多用户协作平台
整体设计与业务逻辑

版本：0.8.0.dev0（remexs/zh-ui 分支）| 更新：2026-08

1. 系统定位

在 Omnigent（多 Agent 协作框架）之上构建的多角色、多用户软件协作平台： 以 项目 为容器、业务任务树（Job） 为管理骨架、Agent 会话（Conversation） 为执行引擎， 由 调度者（admin/项目经理） 编排、执行者 在各自主机上处理、评审者 把关质量的完整闭环。

一句话流程：admin 建项目 + 配流程 → 分配任务给成员 → 成员在自己的机器上领取执行（Agent 干活）→ 自动待评价 → 评审通过/打回重做 → 阶段完成自动下发下一阶段。

│  • 状态机：todo → in_progress → pending_review → completed    │
│                     ↘ returned（打回重做 round+1）             │
│  • 分配：assignee_user_id（谁做）                             │
│  • 执行：host_id（在哪台机器）+ session_id（关联会话）          │

└──────────────────────────────────────────────────────────────┘

3. 权限模型（核心设计）

3.1 两个维度：可见性 vs 执行权

维度存储控制共享后的行为
可见性（谁能看）session_permissions.level ≥ READowner grant被共享者能看消息/产物
参与度（谁能发消息）level ≥ EDITowner grant被共享者能参与会话
执行逻辑（谁的 Agent）conv.agent_id（会话固定）创建者永远用创建者的 Agent
执行环境（谁的机器）conv.host_id（会话固定）创建者永远在创建者的 host
管理（谁能共享）level ≥ MANAGEowner grant可再共享给他人

3.2 权限级别

LEVEL_READ   = 1   # 只读（看消息/产物）
LEVEL_EDIT   = 2   # 可参与（发消息/执行）
LEVEL_MANAGE = 3   # 可管理（共享给他人）
LEVEL_OWNER  = 4   # 所有者（归档/删除/批准）

3.3 任务执行权限（本次新增）

核心规则：执行权 = 主机所有者
  • 调度者（admin）：可见全部 host（调度视角），但不能在别人的机器上执行 —— launch 校验 403
  • 执行者：只能在自己的 host 上 launch（host owner 校验）
  • 任务转发：admin 分配任务给 zhangsan → zhangsan 在自己的 host 领取执行
  • 可选审批：require_approval=true 的任务，领取后进 blocked，admin 批准后才能执行

3.4 项目可见性

对象可见范围
个人项目（kind=personal）仅 owner（会话分组）
团队项目（kind=team）项目成员可见（含 owner + members）
项目任务项目成员可见（scope=project）
个人任务assignee 可见
任务会话assignee + host owner（grant 授权）

4. 状态机

4.1 任务状态（jobs.state）

                    ┌──────────────┐
        创建        │    todo      │
        ──────────► │  （待办）     │
                    └──────┬───────┘
                           │ claim（领取）
                           ▼
                    ┌──────────────┐     require_approval=true 时
                    │ in_progress  │ ──► blocked（等待审批）──admin 批准──► in_progress
                    └──────┬───────┘
                           │ agent 执行完成（自动）
                           ▼
                    ┌──────────────┐
                    │pending_review│ ←── complete / persist_job_completion
                    └──────┬───────┘
                           │ evaluate
              ┌────────────┴────────────┐
              ▼                         ▼
      ┌──────────────┐          ┌──────────────┐
      │  completed   │          │  returned    │  ← 打回，round+1
      │  （已完成）   │          │  （打回）     │
      └──────────────┘          └──────┬───────┘
                                        │ 重新 claim → in_progress（重做）
                                        ▼
                              （回到 in_progress，round 已 +1）

4.2 流程自动派生（项目流程模板）

项目 config.phases 定义有序阶段，阶段任务评价 pass 后自动创建下一阶段任务： 
config.phases = [
  {name:"需求分析", assignee:"zhangsan", agent:"pi-native-ui"},
  {name:"架构设计", assignee:"wangwu",   agent:"pi-native-ui"},
  {name:"后端开发", assignee:"zhaoliu",  agent:"pi-native-ui"},
  {name:"前端开发", assignee:"lisi",     agent:"pi-native-ui"},
  {name:"测试验证", assignee:"admin",    agent:"pi-native-ui"}
]
需求分析 pass ✅ → 自动创建「架构设计」(wangwu) → pass → 自动创建「后端开发」(zhaoliu) → ...

5. 数据模型

5.1 表结构

users（用户，全局公用）
├── id / is_admin / password_hash ...

projects（项目）
├── id / name / owner_user_id
├── kind（'personal' 个人 | 'team' 团队）
└── config（JSON：流程模板 phases[] 等）

project_members（项目成员）
├── project_id / user_id / role（1=成员 2=管理员 3=观察者）
└── created_at

jobs（业务任务树）
├── id / parent_job_id / root_job_id（树结构）
├── title / description / state / round
├── assignee_user_id（谁做）/ created_by_user_id
├── agent_name（执行角色）/ depends_on
├── session_id（关联会话）/ host_id（执行机器）
├── require_approval（执行门禁）/ project_id（归属项目）
└── created_at / updated_at

job_artifacts（任务产物）
├── job_id / artifact_type（file|message）/ ref / summary
└── created_at

job_evaluations（任务评价）
├── job_id / action（pass|reject）/ evaluator_user_id / comment
└── created_at

conversations（会话 = Agent 执行记录）
├── id / title / agent_id（执行逻辑）/ host_id（执行环境）
├── root_conversation_id / parent_conversation_id（会话树）
└── workspace_id

session_permissions（会话权限）
├── conversation_id / user_id / level（1-4）
└── can_approve（审批委托）

5.2 核心关联

Project ──project_id──► Job（根任务 + 子任务树）
                          │ session_id
                          ▼
                     Conversation（Agent 执行会话）
                          │ agent_id ──► Agent 定义（谁执行逻辑）
                          │ host_id  ──► Host（谁的机器）

6. API 设计

6.1 任务（Jobs）— /v1/jobs

方法路径说明
GET/v1/jobs任务列表：roots 默认；scope=assigned（我的）；scope=project（项目任务）
POST/v1/jobs创建任务（含 parent/assignee/require_approval/project_id）
GET/v1/jobs/{id}任务详情（含产物/评价）
GET/v1/jobs/tree/{root}任务树
GET/v1/jobs/stats统计（总数/状态分布/轮次/打回）
POST/v1/jobs/{id}/claim领取（assignee + in_progress；审批任务→blocked）
POST/v1/jobs/{id}/approve-execution批准执行（admin，blocked→in_progress）
POST/v1/jobs/{id}/launch启动执行（host owner 校验 → 建会话 → 派发）
POST/v1/jobs/{id}/complete标记完成（→pending_review + 产物）
POST/v1/jobs/{id}/evaluate评价（pass→completed 触发流程派生；reject→returned+round）
POST/v1/jobs/{id}/state手动改状态
DELETE/v1/jobs/{id}删除

6.2 项目（Projects）— /v1/projects

方法路径说明
POST/v1/projects创建（kind=personal|team，config 存 phases）
GET/v1/projects?scope=mine我的项目（创建 + 成员）
GET/v1/projects/{id}详情（含成员）
PATCH/v1/projects/{id}更新（名称/config/kind）
DELETE/v1/projects/{id}删除
POST/v1/projects/{id}/members添加成员（owner/admin）
DELETE/v1/projects/{id}/members/{uid}移除成员
GET/v1/projects/{id}/members成员列表

6.3 主机（Hosts）— /v1/hosts

方法路径说明
GET/v1/hostshost 列表（admin 见全部含 owner；普通用户见自己）
GET/v1/hosts/{id}/filesystem文件系统（admin 可浏览任意 host，普通用户仅自己的）

12. 设计原则（决策记录）

  • 命名 job（非 task）：避开框架内部 tasks 表，贴合 Databricks Jobs 标准
  • 产物评价独立：job_evaluations（产物质量裁决）与会话评价（审批/评论）完全分离
  • 外层共享不改机制：任务表记"意图"（assignee），领取执行时调用现有 grant() 落地授权
  • host 权限私有：host.user_id != user_id → 403；admin 可见但不可执行别人的机器
  • provider 统一：公司统一模型网关（opencode-go），harness 由个人决定（统一 pi）
  • SkillHub 只协调：技能内容在 SkillHub，Omnigent 只记录/协调不托管
