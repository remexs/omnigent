Omnigent 多角色任务协作架构设计

业务任务树 + 会话执行树 · 产物评价 · 任务流转 · 共享协作
新增：外层业务任务层 复用：会话共享/执行 保留：现有评价不动

1. 设计目标

🎯 解决的问题

将 Omnigent 从"会话为中心的自动化执行"扩展为"多角色、多用户、可管理的任务协作平台"：

需求现状方案
项目管理人员分配任务❌ 无任务概念✅ 外层业务任务树
任务按角色转发给具体的人⚠️ 仅会话共享✅ 任务分配（assignee）
任务完成后产物质量把关❌ 无产物评价✅ 产物评价（✅/❌+意见）
打回重做（回归）❌ 无✅ 评价驱动任务流转
大/小任务、并行执行⚠️ 会话可并行✅ 任务树 + 依赖 + 并行
任务量统计❌ 无✅ 按任务树聚合

2. 总体架构：双维度任务树

🏗️ 两个维度，各司其职
┌─ 外层：业务任务树（管理维度）
│ T1 业务需求（大任务）
│ ├─ T1-R1-t1 需求分析 ← 状态/分配/评价/轮次
│ ├─ T1-R1-t2 架构设计 ← 人看的：项目经理分配、评审评价
│ └─ T1-R1-t3 实现（并行子任务）
│ ├─ T1-R1-t3-1 后端
│ └─ T1-R1-t3-2 前端
│ （子任务可并行执行）
│ ↕ 任务 ↔ 会话映射
└─ 内层：会话执行树（执行维度）
root_conversation（现有）
├─ architect 子会话 ← harness 执行/工具/审批/评论
├─ backend 子会话 ← agent 跑的：怎么执行
└─ ...
维度粒度使用者管理生命周期
外层业务任务树大（需求/架构/实现/测试）人（项目经理/评审）状态/分配/评价/统计任务（可多轮打回）
内层会话执行树细（大脑→子agent→工具）agent（编排器/harness）执行/上下文/工具会话（执行一次）

3. 评价体系：三个独立概念

📋 会话评价（现有·保留）≠ 产物评价（新增）

① 会话评价（现有，保留不动）

过程内 agent 执行过程中的把关

  • 审批（elicitation）：高风险/成本/阶段拦截
  • 文件评论（review comments）：锚定代码文本的修改意见

管"怎么做"的过程质量——完全保留，不参与新任务体系。

② 产物评价（新增，独立体系）

任务后 任务完成后的产物质量把关

  • 评价对象：任务产出的产物（需求报告/架构文档/代码/测试报告）
  • 评价动作：✅ 通过 / ❌ 打回 + 质量意见
  • 评价人：项目经理/评审人
  • 评价历史：每次评价持久记录

管"产物算不算数"的质量裁决——驱动任务流转。

③ 任务（流程单位，衔接两者）

任务本身不是评价对象，是流程单位——完成→产出→评价→流转。

4. 任务流转状态机

🔄 状态流转（产物评价为闸门）
待办（规划）→ 进行中→ 待评价→ ✅ 通过 → 已完成/解锁下游
待评价→ ❌ 打回→ 重做（轮次+1）→ 进行中
状态说明触发
todo 待办任务创建/分配项目经理建任务
in_progress 进行中领取执行（创建内层会话）负责人领取/自动派发
pending_review 待评价完成，等待产物评价会话执行完成
completed 已完成产物评价通过评价 ✅
returned 打回产物评价不通过，回归重做评价 ❌
blocked 阻塞依赖未就绪/等待他人依赖任务未完成

5. 任务树与并行执行

🌳 大/小任务 + 并行 + 依赖
T1 业务需求（大任务·根）
├─ t1 需求分析（串行第一步）
├─ t2 架构设计 depends_on: t1
└─ t3 实现（可拆并行）
   ├─ t3-1 后端 depends_on: t2 ← 并行执行
   └─ t3-2 前端 depends_on: t2 ← 并行执行（同一层独立子任务）
   └─ t3-3 测试 depends_on: [t3-1, t3-2]
机制设计复用现有
大/小任务tasks.parent_task_id✅ 会话树 parent_conversation_id
并行同一父任务独立子任务并发✅ 独立 title 子会话并发
依赖depends_on 字段— 新增
父任务完成所有子任务完成后才"待评价"— 新增聚合逻辑
打回范围子任务打回只重做自己，兄弟任务不受影响— 新增

并行执行复用现有能力："Use a distinct task-based title for independent parallel work"——不同 title 的子会话天然可并行。

6. 共享与协作（不改现有机制）

🔗 外层任务共享 = 意图记录 + 复用现有授权
// 现有机制（复用，零改动）
PermissionStore.grant(
    user_id="lisi",          // 被授予人（评审人）
    conversation_id=conv_id,    // 会话
    level=LEVEL_EDIT,        // 1=读 / 2=编辑 / 3=管理
    can_approve=True,        // 可审批（委托审批权）
)
层职责是否改动现有
外层任务表记录"意图"：assignee（负责人）/ shared_with（共享人）✅ 新增（只存元数据）
内层授权任务领取时调用 grant() 落地权限❌ 不改（直接调用）
会话共享/评论/审批执行层协作照常❌ 不改
设计原则：意图与机制分离——任务表只记"谁该有什么权限"，领取执行时用现有 grant() 落地。现有共享/评论/审批机制零改动。

两个实现细节（已定）

问题决定原因
何时授权？领取执行时（非分配时）分配时可能还没会话，无法授权
子任务继承？默认继承（共享大任务→自动授权所有子任务会话）评审人需要看执行细节

8. 边界：什么不动、什么新增

🧱 清晰的改动边界

✅ 保留不动（现有）

  • 会话执行（harness/runner）
  • 编排器（orchestrator 派发）
  • 会话共享（PermissionStore.grant）
  • 审批（elicitation）
  • 文件评论（review comments）
  • 收件箱
  • tasks 表（运行时内部，不碰）

🆕 新增（外层任务层）

  • tasks 业务任务表（树/状态/分配）
  • task_artifacts 产物登记
  • task_evaluations 产物评价
  • 任务 API（创建/分配/领取/评价/流转）
  • Web 任务列表页 + 评价面板
  • 任务量统计
关键注意：现有 tasks 表（root_task_id/parent_task_id）是运行时 asyncio 内部机制，不是业务任务——业务任务树新建独立表，避免混淆。

9. 端到端执行流程

🚀 从需求到交付
1. 创建  项目经理建大任务 T1 → 拆子任务 t1(需求) t2(架构) t3(实现)
2. 分配  t1 → 张三（assignee），共享给李四（评审）
3. 领取  张三领取 t1 → 创建内层会话（张三的 host）→ grant 权限
4. 执行  会话执行（张三的 harness）→ 产出【需求分析报告】
5. 登记  任务完成 → 登记产物 → 状态"待评价"
6. 评价  李四评价 ✅/❌ + 意见
            ├─ ✅ → t1 完成 → 解锁 t2（架构）
            └─ ❌ → t1 打回 → 轮次+1 → 重新领取执行
7. 并行  t3-1 后端 / t3-2 前端（并行执行）→ 都完成 → t3-3 测试
8. 汇总  大任务 T1 所有子任务完成 → 汇总产物 → 项目经理终评
9. 统计  任务量 = 任务树节点数 / 轮次数 / 打回率
